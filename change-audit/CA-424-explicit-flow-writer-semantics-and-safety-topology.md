## Design notes

- **Self-mapping only, not a new synonym set.** `agent.code`/`contract.freeze` map to themselves, not into any existing canonical id, and no existing alias was retargeted onto them. `agent.code` writer status is a graph-topology invariant the new validator enforces structurally — it is deliberately not an interchangeable synonym like `"coding"`/`"code"` are for `agent.delegate`.
- **`agent.code` reuses `behaviorAgentDelegate` verbatim.** Not a wrapper, not a copy — the exact same registered handler function, same `BehaviorScopeDelegate`. CP-55 §3.5 requires the provider payload stay byte-identical to `agent.delegate`; proven directly by dispatching both ids with the same input and comparing output (`TestAgentCodeReusesDelegateDispatchWithoutChangingProviderPayload`).
- **`contract.freeze`'s placeholder is fail-closed by construction.** It unconditionally returns an error — never `"done"`/`"continue"`, never touches state. CP-55's own P-1 spec permits exactly this ("a fail-closed placeholder handler in P-1 ... it must not silently succeed or mutate state"); the real handler (parse planner draft, validate, bind run/step/baseline, persist durably) is P-3. Nothing dispatches to it today, since no flow node references `contract.freeze` yet.
- **The validator lives in `agentpack`, not `runner`.** `runner` already imports `agentpack` (see `behavior_registry.go`'s own import), so `agentpack` cannot import `runner` — the same dependency-direction constraint CP-55 §3.4 states for `changecontract`/`featurecatalog`. `ValidateFlowSafetyTopology` therefore works on `FlowDefinition.Nodes[].Behavior` (plain strings) via the existing `NormalizeBehaviorID`, not on `runner`'s typed `BehaviorID`. The runner-side `BehaviorAgentCode`/`BehaviorContractFreeze` consts and the agentpack-side string literals are independently declared and independently tested — one cannot silently drift from the other without a test failing on at least one side.
- **Wired once, inside `ValidateFlowDefinition`, not at three call sites.** `ValidateFlowDefinition` already runs at every current definition-resolution boundary (`LoadFlowFS`, and both `FlowDefinitionResolver.ResolveFlowRef`/`ResolveBuiltin`, which call it directly on stored/mirrored records). Adding one call inside it satisfies CP-55's "wire validation at the same definition-resolution boundaries as existing flow/context/artifact validation" with a single low-risk edit instead of three, and keeps the touched-existing-symbol count to exactly three across both packages.
- **Compatibility is structural, not a flag.** `classifyWriterAndFreezeNodes` finds `agent.code`/`contract.freeze` nodes first; zero writers means `ValidateFlowSafetyTopology` returns `nil` immediately, before any graph walk. Since P-1 migrates no flow YAML, every existing flow — built-in or user-defined — has zero `agent.code` nodes today, so every one of them passes. This is proven directly against the real embedded pack (`TestValidateFlowSafetyTopologyAcceptsAllBuiltinFlowsUnchanged`, iterating `LoadBuiltinPack().Flows`), not assumed from the absence of a migration step.
- **Freeze dominance is a real graph-dominance check, not "some freeze exists somewhere."** `ForwardDominates` walks forward from every entry node with the candidate dominator treated as an impassable wall; if the target is still reachable, the candidate does not dominate. `ValidateFlowSafetyTopology` accepts a writer only if *some* `contract.freeze` node dominates it this way — a flow with two freeze nodes on two disjoint branches that both merge into one writer, with neither individually dominating it, correctly fails (this is intentional: CP-55 §3.3/§3.6 binds one frozen contract to one specific writer, and allowing two independently-partial freezes would mean which contract applies depends on which branch executed).
- **CORRECTION (Codex review pass 1, CRITICAL):** the paragraph above described the intended dominance check, but the original `forwardDominatesFrom` did not actually fail closed. Its wall-BFS walked only from the flow's real entries; if the target was never visited by that walk — which is also exactly what happens when the target is unreachable from any entry at all (an absent id, a flow with zero entries, or a writer/freeze pair stranded in a forward cycle disconnected from every real entry) — the function returned `true`, reading "never visited" as "dominated" regardless of *why* it was never visited. A writer/freeze forward cycle with no connection to any real entry therefore passed `ValidateFlowSafetyTopology` outright. The fix adds a `reachableFromAnyEntry` pre-check: both the dominator and target ids must be declared nodes, and the target must be proven reachable from a real entry by an unwalled walk before any dominance verdict is returned. Reproduced and pinned by `TestForwardDominatesRejectsAbsentDominatorID`, `...RejectsAbsentTargetID`, `...RejectsUnreachableWriter`, `...RejectsNoEntryForwardCycle`, `...HandlesMultipleEntriesAllFunnelingThroughDominator`, `...HandlesMultipleEntriesOneBypassingDominator`, `TestValidateFlowSafetyTopologyRejectsNoEntryForwardCycleContainingWriter`, and `...RejectsWriterFreezeCycleDisconnectedFromRealEntries` in `flow_safety_topology_test.go`.
- **`kind=back` edges are excluded from the forward graph**, matching how `ValidateFlowDefinition` already treats them as a retry/reinvoke mechanism rather than a fresh entry-to-target path. This is asserted directly (`TestForwardDominatesIgnoresRetryBackEdgesForEntryDominance`) against a shape mirroring `review-loop.yaml`'s own `synthesis -> coder` continue back-edge.
- **CORRECTION (Codex review pass 1, IMPORTANT):** the original `EveryDonePathIncludesAcceptance` checked only the writer's own direct edges, on the claim that a one-hop check is "logically equivalent to checking every complete path." That claim is false: `writer -> validate -> done` (a non-acceptance intermediate node, then done) is not a direct edge, so it incorrectly passed — the check only ever proved "the writer doesn't edge straight to done," not "every path crosses an acceptance boundary." The fix adds an optional `AcceptanceNodes []string` field to `FlowDefinition` (root YAML key `acceptance_nodes`, additive/`omitempty`-equivalent — every pre-CP-55 flow leaves it unset). A flow declaring any `agent.code` writer must now set at least one entry naming a real, non-writer node (`validateAcceptanceNodes`). `EveryDonePathIncludesAcceptance`/the renamed `everyForwardPathFromWriterCrossesAcceptance` then walks every forward path from the writer's own outgoing edges with state `(node, hasCrossedAcceptance)` — bounded, so a forward-declared cycle downstream of the writer still terminates — and rejects any path that reaches terminal `"done"` before crossing a declared acceptance node. Acceptance crossed only upstream of the writer does not count (the walk never starts before the writer's own successors), and a mixed branch fails if any one branch bypasses acceptance. Verified on 8 new hand-built fixtures (declaration required, unknown id rejected, writer-as-acceptance-id rejected, bypass-via-intermediate rejected, mixed-branch rejected, every-branch-crosses accepted, before-writer-doesn't-count rejected, cycle-after-writer terminates) plus the real `review-loop.yaml` topology loaded via `LoadBuiltinPack()`: `TestEveryDonePathIncludesAcceptanceHandlesReviewLoop` now declares `synthesis` as the acceptance node (both reviewer branches converge there before `done`) and passes, while the new `TestEveryDonePathIncludesAcceptanceRejectsReviewLoopWithoutDeclaredAcceptance` proves the same real topology correctly fails when no acceptance node is declared — which is what review-loop.yaml actually looks like today (P-1 migrates no flow).
- **CORRECTION (Codex review pass 2, IMPORTANT):** the pass-1 fix above still let a writer with no reachable terminal `"done"` at all vacuously pass — a writer with zero successors, or one whose only reachable states loop forever without ever reaching `"done"`, ran out of BFS states to explore and fell through to the function's final `return true`/`return reachedDone` regardless, the same "never found a violation" mistake the pass-1 CRITICAL dominance gap made. The fix adds a `reachedDone` flag set only when a `{done, crossed}` state is actually visited, and the function returns that flag instead of defaulting to safe.
