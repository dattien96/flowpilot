# CA-428 — Move Canonical Mutation To Terminal Flow Acceptance (Task-267, CP-55 P-5)

## Scope

Implemented [Task-267](../requirements/08-Task/done/Task-267-Move-Canonical-Mutation-To-Terminal-Flow-Acceptance.md) (P-5 of [CP-55](../requirements/07-Coding-Plan/done/CP-55-Flow-First-Preflight-Contract-Context-Retrieval-And-Canonical-Acceptance.md)): before this task, `commitChangeContract` wrote the real Canonical Head (`.flowpilot/canonical/<feature_key>.json`) immediately at every gate-passing coder turn — for a multi-turn Flow (planner → coder → reviewer → coder → ... → done), that meant the Head could reflect code later superseded or thrown away entirely, and a Flow stopped/cancelled/failed partway through had already permanently mutated shared feature state. This task adds a `PendingCanonicalStore` that lets a Flow coder child's gate pass STAGE a would-be Head update instead of writing it, and moves the real write to exactly one point: `applyFlowControl`'s `"done"` case, genuine terminal Flow acceptance. Every other outcome (stop/cancel, failure, escalate) either abandons the staged update or leaves it untouched; Normal chat and a Flow's own root/hub turn are completely unaffected (still immediate-write).

A dedicated Claude-agent review (per the operator's standing direction for this phase) found **3 Critical, 8 Important, and 8 Minor findings** against the original implementation — a **FAIL** verdict. All three Critical findings and 6 of the 8 Important findings are fixed in this same note, each verified via mutation testing (temporarily reverted, the corresponding new test confirmed to fail, then restored to pass). See "Claude-agent review pass 1" under Design notes and Verification below for the complete accounting; the two Important findings not fixed (I-4, and the escalate-forever case folded into it) and all 8 Minor findings are explicitly accepted/deferred with reasoning, not silently dropped.

## Design notes

- **Mirrors `FrozenStore`'s proven shape deliberately.** Two append-only NDJSON files, a path-keyed mutex serializing writers across in-process instances, strict reload that fails closed on a corrupt trailing line, and a "logical last-wins status" read model — the same idiom Task-264/265 already established and this codebase's reviewers have already validated once.
- **The routing decision is a single, disjoint boolean at the gate call site**, not a rewrite of `commitChangeContract`'s existing logic: `canonicalRoute := canonicalPendingRoute{}` unless `isCodingChild && s.isFlowEngineDriven(parentID)`. Root/hub gate calls (`runFlowGateAtEpoch`, the legacy `captureChangeContract` fallback) always pass the zero value — Normal chat and a Flow's own hub turn are byte-for-byte unaffected.
- **CORRECTION (Claude-agent review pass 1, Critical — Finding C-1): a key that was ever finalized/abandoned could never become pending again.** `isActiveLocked` trusted only the *Status* of the latest recorded event for a `(run, feature)` key — once that status was terminal, every later `Stage` for the same key was silently invisible to `GetPending`/`ListPendingForRun` forever, even though this codebase explicitly supports a follow-up turn on an already-failed/stopped run (`bug308_stopped_run_followup_allowed_test.go`, `bug302_chat_followup_after_flow_done_test.go`). Concretely: a Flow fails, its pending update is abandoned; the operator redrives the same run, the coder stages a corrected value, the hub reaches "done" — `finalizePendingCanonicalHeadsForRun` would see nothing pending and silently succeed, publishing `done` with the Canonical Head never updated. Fixed: `PendingCanonicalRecord.Seq` (monotonic per store) and `PendingCanonicalStatusEvent.RecordSeq` (the `Seq` of the record a status event resolves) let `isActiveLocked` tell "resolved-and-still-terminal" apart from "re-staged since the last resolution" by comparing sequence numbers, not by reading `Status` in isolation. **Verified via mutation testing**: reverted `isActiveLocked` to the original Status-only check → `TestPendingCanonicalStoreRestageAfterAbandonIsPendingAgain` and `TestFlowFailureThenRedriveThenDoneFinalizesTheNewHead` both failed as expected; restored → both pass.
- **CORRECTION (Claude-agent review pass 1, Critical — Finding C-2): finalize was not atomic across a run's several staged features.** The original `finalizePendingCanonicalHeadsForRun` wrote+marked one feature's real Head at a time; if a later feature in the same "done" batch failed to write (disk full, permission denied, a Drive-sync lock — `.flowpilot/canonical/` is explicitly Drive-synced per `head.go`'s own doc comment), an earlier feature's real Head was already permanently mutated even though the Flow's terminal acceptance — and therefore ALL of its features together — was refused as a whole. Fixed: `StageHeadWrite`/`CommitHeadWrite`/`DiscardHeadWrite` split `SaveHead` into a tmp-file write and a separate rename-into-place; finalize now stages every feature's Head to a tmp file FIRST, and only once every stage in the batch has succeeded does phase two commit (rename) and mark any of them finalized. A staging failure anywhere in the batch discards every tmp file already staged and returns before any real Head is touched. **Verified via mutation testing**: with feature keys chosen so the write-failing one sorts *after* the succeeding one (`ListPendingForRunFresh` returns records sorted by `FeatureKey`, so this ordering is what would let a one-at-a-time finalize write the first before ever reaching the second) — reverted to the original one-at-a-time loop → `TestFinalizePartialFailureCommitsNoHeadInTheBatch` failed exactly as the finding describes (the first feature's Head landed on disk); restored → passes.
- **CORRECTION (Claude-agent review pass 1, Critical — Finding C-3): a finalize failure burned the turn's one-decision slot and left the loop with no operator-actionable path forward.** `lastFlowControlTurnID` is stamped before the `"done"`/`"continue"`/`"escalate"` switch, so a finalize failure inside the `"done"` case returned an error without ever unstamping it — a hub that reasonably retried `flow_control(done)` on the same turn was rejected outright as a duplicate decision, and the loop was left silently `"running"` with no `blocked`/`escalate` state ever published — the same recurring unanswerable-hang failure class this codebase has regressed on before (BUG-288 #9 / Task-242 T-9). Fixed: on finalize failure, `lastFlowControlTurnID` is cleared and `applyFlowControl(escalate)` is called (mirroring `gate_hook.go`'s own commit-failure-escalates precedent) before the error is returned, so the loop reaches `Status="blocked"`/`BlockReason="escalate"` with a `GateReason` naming the failure. **Verified via mutation testing**: reverted to the original bare-error-return → `TestFlowDoneFinalizationFailureEscalatesLoopForOperatorAction` failed (loop stayed `"running"`); restored → passes, loop reaches `blocked`/`escalate`.
- **Addition (Claude-agent review pass 1, Important — Finding I-1): finalize/abandon now reload fresh under a single lock hold before deciding.** `ListPendingForRun` only reflected a `PendingCanonicalStore` instance's original load — a `Stage` call against a *different* in-process instance (e.g. a coder gate pass whose gate epoch was still valid the instant the hub called `"done"`) landing after that snapshot was silently invisible to the finalize/abandon decision. `ListPendingForRunFresh` re-reads both NDJSON files and lists in one locked critical section instead of two; `finalizePendingCanonicalHeadsForRun`/`abandonPendingCanonicalHeadsForRun` now call it.
- **Addition (Claude-agent review pass 1, Important — Finding I-2): `applyFlowControl` no longer reads a shared mutable field outside `s.mu`.** `rs.workspaceCwd` was read in the `"done"` case after `s.mu.Unlock()` — `workspaceCwd` is written during run reconstruction/resume, an unsynchronized concurrent read. Fixed: captured into a local (`flowControlWorkspaceCwd`) while the lock is still held, mirroring `stopAgentLoop`'s own existing pattern for the same field.
- **Addition (Claude-agent review pass 1, Important — Finding I-3): Stop/failure now abandon pending records for direct children too, not only the run itself.** A staging record is keyed by the coder's *immediate* parent run — for a coding child under a sub-hub, that parent is the sub-hub's own run ID, not the root run a Stop/failure was called on. Fixed: `stopAgentLoop` abandons for `parentRunID` plus every ID already collected in `persistChildIDs`; the `EventTurnFailed` handler abandons for the failed root plus `s.agentOrchestrator.listChildren(failedRunID)`. This is deliberately one level deep, matching every other Stop-cascade mechanism already in this file (gateEpoch bump, turn cancellation, etc. are all one-level-deep today) — going further (recursive descendant collection) would be a larger, separate change to the Stop cascade itself, not scoped to this task.
- **Addition (Claude-agent review pass 1, Important — Finding I-5): `Stage` now rejects a `FeatureKey`/`Head.FeatureKey` mismatch.** `SaveHead` derives its target file from `Head.FeatureKey`, not from the record's own `FeatureKey` — today's only caller (`stagePendingCanonicalHead`) always derives both from the same `Contract.FeatureKey` so this was latent, not live, but `computeCanonicalHeadUpdate`'s `found` branch returns `UpdateHead(head, c)`, which propagates the *on-disk* Head's own `FeatureKey` — a hand-edited or Drive-sync-merge-conflicted Head file whose internal field disagrees with its filename would have silently finalized under one tracking key while writing an unexpected file. Fixed: `Stage` fails closed on a mismatch.
- **Addition (Claude-agent review pass 1, Important — Finding I-6): three vacuous tests replaced with discriminating ones.** `TestPendingCanonicalStoreIsIdempotent`'s own comment promised a duplicate-write check it never performed; it now asserts the actual on-disk line count. `TestExplicitRebaselineBehaviorIsUnchanged`/`TestExplicitRetireAndMergeBehaviorIsUnchanged` asserted `GetPending("", ...)` — `Stage` rejects an empty `RunID` unconditionally, so this could never fail regardless of correctness; both now assert the pending-canonical store file never gets created at all.
- **Addition (Claude-agent review pass 1, Important — Finding I-7): two previously-untested paths now have direct coverage.** A Flow's own root/hub turn (`flowEngineDriven=true`, `parentRunID=""`) was safe by construction (`runFlowGateAtEpoch` always passes the zero-value route) but unpinned; `TestFlowRootHubTurnWritesCanonicalHeadImmediately` closes that. The false branch of `isFlowEngineDriven` at the routing site (an ad hoc `spawn_agent` coding target outside any Flow, which keeps immediate-write behavior) was also unpinned; `TestAdHocCodingChildOutsideFlowEngineWritesImmediately` closes that.
- **Addition (Claude-agent review pass 1, Important — Finding I-8): the misnamed stale-epoch test renamed, and a genuine one added.** `TestStaleEpochCannotFinalizeCanonicalHead` actually exercised the duplicate-`"done"`-on-an-already-terminal-loop guard (`interactive_service.go`'s terminal check), which has nothing to do with `gateEpoch` — renamed to `TestDuplicateDoneIsRejectedWithoutRefinalizing`. `TestStaleEpochGatePassDoesNotStagePendingCanonicalUpdate` (new) genuinely exercises `gateEpoch`: it bumps a child run's epoch after capturing the (now stale) value the gate pass is evaluated at, and asserts nothing gets staged — `withGateEpochDurable` is what actually governs this, shared with the rest of `commitChangeContract`'s durability guarantee.
- **Accepted/deferred, not fixed in this pass (Claude-agent review pass 1):**
  - **Finding I-4 (no reaper for a pending record left dangling by a hard kill — no Stop, no `EventTurnFailed`, no graceful path at all — or by an escalate that is never resumed)**: correct as identified. Escalate-forever is legitimate by spec (the record must stay active while a human decision is pending) but a genuinely abandoned workspace (process killed, run never reconstructed) has no sweep today. This is inert, not unsafe — a dangling pending record never causes an incorrect Head write, it only accumulates as clutter — and fixing it properly means a startup/reconstruction-time reconciliation pass across *all* runs, a broader change to the runner's recovery path than this task's own scope. Recorded as an explicit open question for a later housekeeping task, not silently resolved.
  - **Finding M-1 (a doc-less new feature now finalizes as `spec_less` instead of `current`, since the real Head is never written mid-flow for `BuildHead`'s birth path to run against)**: correct, and arguably more accurate (a doc-less feature genuinely has no spec backing it), but an undocumented behavior change nonetheless — recorded here rather than fixed, since "fixing" it would mean re-introducing exactly the immediate-write-per-turn behavior this task exists to remove.
  - **Finding M-2 (spec/code drift detection is effectively off for the whole duration of a Flow whose feature has no pre-existing Head, since the real Head does not appear until "done")**: correct as identified; low real-world impact (a just-minted Head cannot itself be drifted), noted rather than addressed.
  - **Finding M-3 (`abandonPendingCanonicalHeadsForRun` on Stop is not gated on `isFlowEngineDriven`, so a plain Normal-chat Stop now creates an empty `canonical-pending/` directory)**: correct, cosmetic, accepted — `.flowpilot/` is Drive-synced so this does propagate an empty directory, but causes no functional issue.
  - **Finding M-4 (`recordsEqual`'s marshal-error branch returns "not equal" rather than surfacing the error)**: the underlying `Seq`-comparison concern is fixed (recordsEqual now zeroes `Seq` before comparing); the marshal-error-swallow itself is accepted as extremely low-risk, since `Stage`'s own subsequent `json.Marshal(rec)` call surfaces the identical error immediately after.
  - **Finding M-7 (`stageOneCodingPass`'s test helper derives a child ID from `head[:8]`, which would panic on a short/empty SHA)**: correct, accepted as a test-only risk with no production impact — `newContractFreezeTestRepo` always returns a full SHA in every actual run of this suite.
  - **Finding M-8 (`pendingCanonicalLocks` map grows unbounded, one mutex per distinct workspace path, forever)**: correct, mirrors the identical pre-existing shape in `FrozenStore`; negligible at current scale, any future fix should apply to both stores together, not this one alone.
