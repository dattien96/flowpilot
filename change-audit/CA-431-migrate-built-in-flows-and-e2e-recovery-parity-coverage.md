# CA-431 — Migrate Built-In Flows And Add End-to-End Recovery/Parity Coverage (Task-270, CP-55 P-8)

## Scope

Implemented [Task-270](../requirements/08-Task/done/Task-270-Migrate-Built-In-Flows-And-E2E-Recovery-Parity-Coverage.md) (P-8 of [CP-55](../requirements/07-Coding-Plan/done/CP-55-Flow-First-Preflight-Contract-Context-Retrieval-And-Canonical-Acceptance.md)): migrates the three real, production built-in Flow YAMLs (`review-loop`, `rag-harness`, `context-coding-review-synthesis`) to the CP-55 target pattern — a read-only `preflight-contract-plan` (`agent.delegate`) entry node, a `preflight-contract-freeze` (`contract.freeze`) node, then (where the flow already had one) a `context.produce` node, then the writer node promoted from `agent.delegate` to `agent.code` — and proves the whole mechanism end to end: restart/recovery safety across freeze/gate/finalization, cross-provider parity (Claude/Codex/Grok), and zero regression to Normal chat mode.

Research before implementation surfaced a **Critical, previously-shipped gap**: an `agent.code` writer's gate pass could never set `isCodingChild = true` (that flag lived entirely inside a block gated on `isDelegate`, which requires `canonical == "agent.delegate"` — structurally unreachable for `agent.code`), so `commitChangeContract` was never invoked for a frozen `agent.code` writer at all — not "falls back to immediate write," but zero Canonical Head effect, ever. Implementation and the subsequent test-regression fix pass (below) found **two more genuine production bugs** through the same disciplined mutation-testing/full-regression practice this whole CP-55 effort has followed: a pending-canonical-store bookkeeping write that self-triggered scope drift on a writer's own second gate pass (would have self-blocked every real validation/review retry for all three migrated flows), and — found only while fixing test fallout from the migration itself — `advanceFlowThroughFreezeChain` never rendering the built `FlowContextPackage` into the writer's actual prompt when the freeze node edges directly to the writer with no intermediate `context.produce` hop (review-loop's own shape): the package was built and stored on `rs.planContextPackage` (satisfying every test that checked the package itself) but the coder's real prompt was just `rec.Intent`'s bare sentence, silently defeating the entire P-6/P-7 feature-history-ranking mechanism for exactly the flow most users hit first (Chat Mode's "bug" sub-mode).

A dedicated Claude-agent review found **1 Critical, 3 Important, and 2 Minor findings** — a **FAIL verdict**, the most severe of any CP-55 phase reviewed so far: the Critical finding was a real, concretely-demonstrated bypass of CP-55's own central guarantee (that a Flow writer's effect on the Canonical Head system-of-record can only ever result from a gate-reviewed, in-scope turn), reachable with nothing more than the coder's own ordinary file-write tool. All 4 Critical/Important findings are fixed in this same pass and independently mutation-tested; both Minor findings are accepted/documented, not fixed (see Design notes).

## Design notes

- **Verified, not assumed: prepending an `agent.delegate` entry node routes through the standard `entryDelegateNodes` path, not `startInlineEntryChain`'s narrower fallback.** Before editing any YAML, `entryDelegateNodes`/`entryNodesNoDeps`/`startInlineEntryChain` were read in full. `entryDelegateNodes` matches a no-incoming-forward-edge node whose behavior is exactly `agent.delegate` — `preflight_contract_plan` qualifies, so `startResolvedFlow` never falls through to `startInlineEntryChain` for any of the three migrated flows. This was a real risk identified and closed before the YAML edits were made, not discovered by accident afterward.
- **CORRECTION (found during implementation, before any review pass): the `agent.code` writer's gate pass had zero Canonical Head effect, not merely a wrong one.** Every one of CP-55 P-5's own ~20 tests exercised only an `agent.delegate` coding child (by construction — see `flow_pending_canonical_test.go`'s own fixture comment), so this gap was untested until P-8's own research surfaced it by inspection of `isCodingChild`'s exact gating condition. Fixed by adding a parallel path sourced directly from the `FrozenContractRecord` (not the legacy `Contract` parser), consistent with P-4's own separate-lifecycle design decision (Task-264 D-1). Mutation-tested: reverted, confirmed `TestFrozenAgentCodeWriterStagesPendingCanonicalUpdate` fails, restored, confirmed it passes.
- **CORRECTION (found during implementation, before any review pass): a frozen writer's own pending-canonical staging write self-triggered scope drift on its very next gate pass.** `.flowpilot/canonical-pending/pending_canonical.ndjson` was not in `IsFrozenStoreBookkeepingPath`'s exemption list, so any validation-retry or review-loop retry for a migrated flow would self-block, every time — undetected until P-8 because no P-4/P-5 test ever drove more than one gate pass against the same frozen contract. Fixed with an exact-file-match-only exemption (preserving CA-427 Finding 2's directory-exemption security fix). Mutation-tested: reverted the new OR-clause, confirmed `TestFrozenAgentCodeWriterSecondGatePassDoesNotSelfTriggerDrift` fails, restored, confirmed it passes.
- **CORRECTION (found while fixing test fallout from the migration, before any review pass): `advanceFlowThroughFreezeChain` never rendered the built `FlowContextPackage` into the writer's actual prompt when `path` was empty — review-loop's own shape (freeze edges directly to `coder`, no `context.produce` hop).** The function built and stored `rs.planContextPackage` only inside the `for _, mid := range path` loop; when that loop never ran, the writer's prompt was composed as `composeFlowNodeAgentPrompt(workspace, rec.Intent, writerNode)` — the frozen contract's bare intent sentence, with no source excerpts and no feature-history block at all. This satisfied every P-8 e2e test written so far (`TestFirstCoderContextUsesCurrentFlowDeclaredPaths`/`TestFirstCoderContextRanksFeatureHistoryByCurrentLocus` both use `freezeChainWithContextFixture`, a fixture that deliberately includes a context node, and check the built *package*, not the delivered prompt text) — masking the gap for exactly the shape review-loop actually has. It surfaced only because `TestFlowCodingPromptSpawnWrappedDoesNotDuplicateHistory` (an existing, pre-P-8 test, not one of P-8's own 18) asserts on the coder's *actual delivered prompt* and uses rag-harness (which does have a context node) — investigating its failure led to discovering the SAME code path silently skips context entirely for review-loop. Fixed: a package is now always built (falling back to the writer's own `ContextSources` when the mid-hop loop never ran) and rendered into the writer's prompt via `renderFlowContextPromptWithSecret`, the same behavior `startInlineEntryChain` already had for the old topology. Verified via the full existing `TestFirstCoderContext*`/`TestFrozenAgentCodeWriter*`/`TestClaudePreflightContract*` suites (all still green — the fix is additive for the fixtures that already had a context node) plus the newly-passing `TestFlowCodingPromptSpawnWrappedDoesNotDuplicateHistory` (which now genuinely proves the FCP block reaches review-loop's own coder).
- **Known, disclosed asymmetry, not a defect: review-loop has no `context.produce` node; rag-harness and context-coding-review-synthesis do.** The CP-55 spec's own illustrative target pattern names `context: context.produce` as a step in the canonical shape, but review-loop never had a context-producing node before this migration and none was added — the `advanceFlowThroughFreezeChain` fix above makes this safe regardless (the writer always gets a rendered package either way), so migrating review-loop with the spec's fixed shape verbatim was judged unnecessary additional surface area for this phase. Recorded here explicitly rather than left as a silent inconsistency; a later phase could add an explicit `context` node to review-loop for topological uniformity with the other two flows, but nothing about correctness depends on it now.
- **The shared fake-adapter fix (`fake_provider_adapter.go`) is a real demo-mode fix, not test-only scaffolding.** `DefaultProviderRegistry` — registered by `NewInteractiveService()`, the production constructor — backs Codex with this exact fake adapter whenever the real Codex app-server path isn't enabled (`ProviderRegistryFor`'s own doc comment: "demo/tests stay green without a codex binary"). Without recognizing the contract-planner's turn, a real user running any of the three migrated flows in demo/no-credentials mode would have hit a freeze failure on literally the first turn, every time.
- **CORRECTION (Claude-agent review pass 1, Critical Finding 1): a coder's ordinary file-write tool could forge an arbitrary Canonical Head for any feature, completely bypassing scope enforcement.** `IsFrozenStoreBookkeepingPath`/`IsPendingCanonicalStoreBookkeepingPath` exempt exact bookkeeping paths from the gate's scope-drift comparison (necessarily — a writer's own legitimate staging write must not count against itself, per this same phase's own P-5 fix above) — but exempting a path from drift detection ALSO means its CONTENTS were never otherwise checked. `finalizePendingCanonicalHeadsForRun` read every still-pending record via `ListPendingForRunFresh` and wrote `rec.Head` byte-for-byte to the real Canonical Head file with zero cross-check that the record came from a legitimate `Stage()` call versus a raw NDJSON line an agent's own write tool appended directly to `.flowpilot/canonical-pending/pending_canonical.ndjson` — for an entirely unrelated `feature_key` the frozen contract never declared anything about. The reviewer's own suggested fix (HMAC-bind records using the same `markerSecret` infrastructure already used for the FCP prompt marker) was adopted directly: `PendingCanonicalRecord.Signature`, `NewPendingCanonicalStoreWithSecret`, and an `isActiveLocked` verification gate close it. A narrower alternative considered and rejected — cross-checking each pending record against `FrozenStore` at finalize time — would have broken the pre-existing, legitimate P-5 path where an ordinary `agent.delegate` coding child (no frozen contract involved at all) stages a pending Canonical Head update; the chosen HMAC fix protects both paths uniformly. The analogous, narrower pre-existing gap in `FrozenStore`'s own bookkeeping-path exemption (a coder forging `frozen_contracts.ndjson` directly to self-widen its own declared scope) predates P-8 and is explicitly out of scope for this fix — recorded as a candidate for a dedicated future hardening task, not silently bundled in here.
- **CORRECTION (Claude-agent review pass 1, Important Finding 2): the fake-adapter's role-marker match was an unanchored substring, collidable with a custom agent's own role.** `strings.Contains(prompt, "role: contract-planner")` would also match a user-cloned custom agent whose role merely starts with that text (e.g. `"contract-planner-v2"`) — such an agent would silently receive the hardcoded generic JSON draft instead of its own intended turn output, with no error surfaced. Fixed by anchoring on the pipe delimiters `composeAgentIdentityLine` always emits around each identity-line part (`"| role: contract-planner |"`), which a same-prefixed-but-different role can never produce.
- **CORRECTION (Claude-agent review pass 1, Important Finding 3): `ResolvedFeatureKey` was trusted as `ConfidenceVerified` with no cross-check, and the planner's `feature_key` is deliberately unvalidated upstream too.** `runContractFreezeNode` intentionally does not allowlist the planner's `feature_key` against the catalog ("trusted for now" — a P-3 design decision, CA-426). Combined with P-8's own unconditional `ConfidenceVerified` marking, a planner LLM that hallucinated or mis-selected a `feature_key` colliding with a real, but wrong, existing feature would silently and confidently route `feature.history` to the wrong feature's history, with no warning anywhere in the pipeline. Rejecting an unrecognized key outright was considered and rejected — it would break two legitimate cases: a planner naming a genuinely NEW feature not in the catalog yet, and a project with no catalog built at all (a normal early-project state, not a validation signal against this specific key). Fixed with a narrower check: downgrade to `ConfidenceLow` only when the catalog loads successfully AND positively lacks the key; a load failure keeps the value trusted unchanged. A brand-new feature has no history to rank anyway, so nothing legitimate is lost; an existing-but-wrong collision no longer masquerades as independently verified. **Mutation-testing note**: the first implementation attempt downgraded confidence on ANY catalog-load failure too, which broke `TestFirstCoderContextRanksFeatureHistoryByCurrentLocus` and 3 other pre-existing P-8 tests (`newContractFreezeTestRepo`'s fixture never builds a catalog file at all) — caught immediately by the existing regression suite before it was ever considered a candidate fix, and corrected to the load-failure-keeps-trusted design described above.
- **CORRECTION (Claude-agent review pass 1, Important Finding 4): the P-8 Canonical Head fix was only reachable via incidental coupling to unrelated always-on default rules.** For a frozen `agent.code` writer, the flowgate rule subset `only` is populated ONLY by the unconditional artifact-rule scan (`r-artifact-output`/`-structure`/`-telegram-sent`) — the doc-scope/test-rule block is deliberately never entered for it (scope enforcement for a frozen writer is the hardcoded frozen-contract check, not the configurable rules engine — see the `isCodingChild = true` comment above). `if len(only) == 0 { return false }` had no `!isCodingChild` guard, unlike the two nearly-identical no-op checks immediately below it that already did — so a workspace that ever disables all three artifact rules (a plausible cleanup for a flow with no artifact bindings, like review-loop) would discard the frozen writer's prepared Canonical Head effect silently, recreating the exact bug this phase's own core fix exists to close, just conditionally on rule configuration. Fixed by adding the matching guard. **Mutation-testing note**: the regression test for this fix (`TestFrozenAgentCodeWriterStagesCanonicalUpdateEvenWithArtifactRulesDisabled`) initially failed for an unrelated reason on first write — writing a custom `flow-rules.json` directly into the frozen contract's own git workspace, without committing it, made the file itself look like an out-of-scope write to the (unrelated, already-correct) scope-drift check, blocking the turn before ever reaching the code path under test.
