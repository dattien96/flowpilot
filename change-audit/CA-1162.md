# CA-1162 — BUG-631 extend-cap effective cap survives remount

## Context

Live run-150388: loop state showed `extendCount:31` yet `cap:5` (the
policy default). Thirty-one operator extend-cap grants, zero effect —
the `escalate → extend → continue` operator path was a dead letter:
every re-mount reseated the cap, the loop re-blocked on the same
boundary, and the card reappeared.

Defect: `extendCap` correctly mutates durable loop state
(`st.Cap += ExtendBy`, `ExtendCount++`, persisted via
`persistParentSession`), but `startResolvedFlowFromNode`'s mount
mutation unconditionally reseated `st.Cap = Definition.Policy.Cap`
on every mount — debate re-mount, sprint re-mount, post-restart flow
start all wiped the grant.

## Changes

`internal/runner/flow_executor.go` — the mount mutation now skips the
Cap/RoundCap reseed when the loop carries an operator grant larger than
the policy value:

```go
if st.ExtendCount == 0 || st.Cap < cap {
    st.Cap = cap
    st.RoundCap = cap
}
```

Semantics preserved:
- Fresh mounts (`ExtendCount == 0`) seed from the flow's own policy —
  `TestStartResolvedFlowAppliesConfiguredCapAndExtendBy` unchanged.
- A reconfigured LARGER policy cap still wins (`st.Cap < cap` → reseed)
  — reconfiguration is headroom growth, never a shrink.
- `ExtendBy`/`NegotiationCap` remain config seeds, always refreshed.
- Grants are run-scoped: `ExtendCount` and `Cap` are durable per-run
  loop state, so the guard applies uniformly across debate/sprint/
  ingest remounts on the same parent run.

## Regression test

`internal/runner/bug631_extend_cap_reseed_test.go`:
- `TestBug631_ExtendCapSurvivesRemount` — mount (cap=3) → extend (cap=5,
  ExtendCount=1) → `startResolvedFlow` again → asserts Cap=5. Red before
  the fix (`Cap = 3, want 5`), green after.
- `TestBug631_RemountAdoptsLargerPolicyCap` — extend then raise the
  policy cap to 9 → remount → asserts Cap=9 (guard prevents shrink only).
