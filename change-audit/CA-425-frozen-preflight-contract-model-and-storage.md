## Design notes

- **Two lifecycles, not one extended.** `changecontract.Contract` (Task-184) is a tolerant, mutable-by-overwrite, last-wins-by-`(run_id,step_id)` capture read by chat-mode context injection and the legacy r-contract/r-scope gate — its own doc comment states callers should treat a `Save` error as "capture degraded," never as a reason to block. CP-55's Flow preflight needs the opposite invariants: immutable after freeze, versioned, strict-reload. Bolting the second set of invariants onto the first type would either weaken every existing tolerant caller or require a mode flag threading through `Contract`/`Store`; two independent types with two independent NDJSON files under the same `.flowpilot/contracts/` directory (`frozen_contracts.ndjson`, `frozen_contract_events.ndjson`, both new) avoids that, at the cost of some structural duplication (both have a `FeatureKey`/`Intent`/`DeclaredPaths` shape) which is an acceptable, explicit tradeoff given the HIGH GitNexus fan-in on the type this avoids touching.
- **`ParsePreflightDraft`'s trailing-content check relies on `json.Decoder.More()` at the top level, not inside an array/object.** After a successful `Decode`, `More()` peeks the next non-whitespace byte in the stream; at the top level (no enclosing composite being scanned), any remaining non-whitespace content — valid JSON or not — makes it return `true`. This is the same idiom the standard library itself documents for decoding a concatenated stream of JSON values (`for dec.More() { dec.Decode(&v) }`); here it is used once, after one `Decode`, purely to detect "is there anything left" rather than to decode a second value. Verified directly: `TestParsePreflightDraftRejectsTrailingProse` feeds `{...} thanks!` and confirms rejection; `TestParsePreflightDraftAcceptsSurroundingWhitespace` confirms leading/trailing whitespace alone does not trip it.
- **`NormalizeDeclaredCodePaths`'s absolute-path bug, caught by its own test before this note was written.** The first implementation detected "is this path absolute" via `path.IsAbs` (the POSIX-only `"path"` package) on a string already converted to forward slashes via `filepath.ToSlash`. On Windows, an absolute path looks like `C:/Users/.../foo.go` — `path.IsAbs` only recognizes a leading `/`, so it returned `false` for a genuine Windows absolute path, silently skipping both the outside-workspace rejection and the workspace-relative rewrite. `TestNormalizeDeclaredCodePathsRejectsAbsoluteOutsideWorkspace` and `TestNormalizeDeclaredCodePathsAcceptsAbsoluteInsideWorkspace` both failed immediately on first run (Windows dev environment), diagnosing exactly this. Fixed by detecting absolute-ness via `filepath.IsAbs` on the OS-native form (`filepath.Clean(filepath.FromSlash(trimmed))`) before any slash conversion, then converting to forward-slash only after the workspace-relative rewrite. Both tests pass after the fix; the full `paths_test.go`/`preflight_test.go` suite (102 tests total in the package) is green.
- **Two kinds of rejection in `NormalizeDeclaredCodePaths`, not unified into one error path.** Workspace escape (absolute-outside, `../` traversal, symlink resolving outside) fails the entire call on the first offending entry — a security boundary, where "drop the bad one and keep going" would silently narrow a Flow's declared scope without telling anyone. "Not concrete" (glob, bucket, doc, flag-like) is filtered per-entry via the same `IsConcreteCodeTarget` predicate `buildRetrievalLocus` already applies non-fatally — an all-noise input (e.g. all globs) surfaces as the same "no concrete code path declared" error the empty-input case gets, since once every entry is filtered there is nothing more specific left to name. `TestNormalizeDeclaredCodePathsRejectsGlobOnlyScope`/`...RejectsDocumentOnlyWriterScope`/`...RejectsBucketOnlyScope` cover the all-noise cases; `TestNormalizeDeclaredCodePathsMixedNoiseAndConcreteKeepsConcrete` proves a mixed list keeps only the concrete survivor rather than erroring on the noise.
- **Symlink-escape check is best-effort by construction, not a gap.** `filepath.EvalSymlinks` is only called when the target already exists on disk; a declared path for a file the coder hasn't created yet (the common case for a frozen preflight scope) fails to resolve and the check is skipped rather than treated as an error — `TestNormalizeDeclaredCodePathsToBeCreatedFileSkipsSymlinkCheck` pins this. The actual symlink-escape rejection test (`TestNormalizeDeclaredCodePathsRejectsSymlinkEscape`) skips itself on Windows (`runtime.GOOS == "windows"`) since creating a symlink there requires elevated privileges the CI/dev environment does not reliably have; it is written to run on POSIX environments where this repo's tests execute.
- **`SaveFrozen` idempotency compares marshaled JSON bytes, not `reflect.DeepEqual`.** The frozen design decision explicitly said "byte-equivalent payload is idempotent" — `frozenRecordsEqual` marshals both records and compares the resulting byte slices, which is both what the design asked for and avoids any ambiguity around `time.Time` internal representation (monotonic reading) that `reflect.DeepEqual` could trip on for two structurally-equal-but-differently-constructed timestamps.
- **`GetFrozenForStep` does the active-version reduction itself; `ListVersionsForStep` does not.** The former sorts a step's versions ascending, then walks from the highest down, returning the first whose latest status event is neither `superseded` nor `abandoned` (no status event at all counts as active — a fresh freeze with nothing recorded against it yet). The latter returns every version, unreduced, for audit/debugging. `TestGetFrozenForStepReturnsLatestActiveVersion` freezes v1, confirms v1 is active, then freezes v2 as an amendment and marks v1 `superseded`, confirming the same call now returns v2. `TestGetFrozenForStepReturnsNotOkWhenEveryVersionInactive` confirms an all-abandoned step reports `ok=false` rather than returning a stale record.
- **Cross-instance write serialization uses a package-level path-keyed lock, not per-instance locking alone.** `frozenStoreLocks` (a plain `map[string]*sync.Mutex` guarded by its own `frozenStoreLocksMu`) is looked up by the store's absolute `frozen_contracts.ndjson` path at `NewFrozenStore` construction time, so two independently-constructed `*FrozenStore` values rooted at the same workspace share the same `*sync.Mutex`. `TestFrozenStoreConcurrentInstancesDoNotInterleave` launches 20 goroutines, each constructing its own `*FrozenStore` and calling `SaveFrozen` with a distinct contract id, then reloads via a 21st fresh instance and asserts exactly 20 records — proving no torn/interleaved append under concurrent same-process access. Multi-process locking is explicitly not attempted — documented in both this note and Task-264 as a P-3/P-4 prerequisite the runner process boundary must decide, matching the frozen design decision's own instruction not to copy the runner's private flock implementation into this package.
- **Strict reload is genuinely fail-closed, verified by a real corrupt line, not just asserted.** `TestFrozenStoreCorruptContractsLineFailsClosed` and `...CorruptEventsLineFailsClosed` each freeze/append a valid record first, then append a hand-written invalid JSON line directly to the NDJSON file, then construct a fresh `NewFrozenStore` and assert it returns an error — proving the strict-reload behavior actually triggers on real corrupt bytes rather than relying on inspection of the `json.Unmarshal` error-handling branch alone.
- **The legacy `Contract`/`Store` lifecycle's isolation is proven, not assumed.** `TestContractStoreLoadsLegacyRecordsWithoutNewFields` saves a legacy `Contract` via `NewStore`, then opens a `FrozenStore` at the same workspace and confirms `GetFrozenForStep` finds nothing (the two stores read different files), then reloads the legacy `Store` again and confirms its own record is still there unaffected — both directions checked, not just one.
