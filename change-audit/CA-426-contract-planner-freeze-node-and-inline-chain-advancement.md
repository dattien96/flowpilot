## Design notes

- **The registry-level `contract.freeze` stub is deliberately left untouched.** `behaviorContractFreezeNotImplemented` (Task-263) is never reached through `BehaviorRegistry.Dispatch` in practice — the real logic dispatches from `tryAdvanceFlowThroughInline`'s switch directly, exactly mirroring how `command.validate`/`artifact.audit_draft`/`telegram.notify`/`hub.notify` already work in this same file. This keeps the registry's type-check role (confirming an id resolves to a registered `BehaviorScopeInline` spec, used by `resolveFreezeWriterTarget` itself) separate from "what actually happens," which is this file's job.
- **`resolveFreezeWriterTarget` is pure by design so the two adversarial-graph cases (hop limit, cycle) are unit-testable without any service/provider/git fixture.** `TestInlineChainStopsAtHopLimit` builds an 8-hop chain (`h1`..`h7` then `coder`) — one hop past the 6-hop limit — and asserts `ok=false`; `TestInlineChainDetectsCycle` builds `freeze -> a -> b -> a` and asserts the same. Both run in under a millisecond, no git/provider setup.
- **Planner-mutation enforcement's correctness depends on the planner being the flow's entry node.** `rs.flowStartGitHead` is captured once, before any node in the flow runs (`flow_executor.go:80-82`, pre-existing). If a future flow topology inserted some other writer-capable node *before* the planner, this check would attribute that node's changes to the planner too — not a concern for any topology this task's own tests or CP-55's design use (planner is always entry), but worth flagging for P-8's real built-in-flow migration to preserve.
- **`context.produce` dispatched as a real hop, verified by an actual working coder-prompt continuation.** `TestRunContractFreezeNodeAdvancesToContextProduce` and `TestInlineChainAdvancesFreezeThenContextThenWriter` both use the `freeze -> context -> coder` fixture and assert the coder child actually spawns (via `waitLoop`/`countChildrenWithLabel`) — proving `BuildFlowContextPackageWithSources` succeeding is a precondition for reaching the writer, not merely that the code compiles.
- **Duplicate-delivery reuse is proven with a *different* planner draft on the second call, not the same one.** `TestRecoveredFlowReusesPersistedFrozenContract` pre-seeds a frozen record with `Intent: "original intent"`, then calls `runContractFreezeNode` with a draft carrying `Intent: "a completely different intent"` and different `declared_paths` — and asserts the store still has exactly one version, with the *original* intent. This is the strongest form of the proof: if the reuse check were missing or backwards, this test would either see two versions or see the new (wrong) intent win.
- **Physical writer re-spawn on duplicate delivery is knowingly not de-duplicated — this is not a regression, it is the pre-existing codebase norm.** Verified directly: `tryAdvanceFlowFromNode`'s own spawn loop (`flow_executor.go`) only reuses an existing child when the target node declares `Lifecycle: "reinvoke"` (`flowNodeReusesChild`); a plain node re-completing always spawns fresh in the existing, already-shipped code. `contract.freeze`'s writer node in this task's fixtures declares no lifecycle, so it inherits that identical always-fresh-spawn behavior — no new gap introduced relative to what already ships. See Task-265 D-6.
- **`baselineWorktreeFingerprint` reuses `uncommittedChangedPaths` (Task-246) rather than re-implementing git-dirty detection**, keeping the "what changed" logic in one place across CP-54's retrieval-locus builder and CP-55's baseline fingerprint. An unreadable path yields an empty-string fingerprint entry (best-effort, matching Task-264 D-2's own "runner captures it in P-3" note) rather than failing the whole freeze over one unreadable file.

**Claude-agent review pass 1 (2026-07-31):** a dedicated Claude reviewer agent (invoked via the Agent tool with `subagent_type: reviewer-agent`, per operator direction to use a Claude agent rather than Codex) found 4 Critical, 11 Important, and 7 Minor findings against the original implementation above. All 4 Critical and the Important findings actionable within P-3's own scope are fixed; the rest are recorded as accepted/deferred with reasoning, not silently dropped.

- **CORRECTION (Critical, C-1): the planner-mutation check fired on ANY dirty worktree, not on the planner's own mutations.** `changedFilesSince(workspace, baseSHA)` → `flowgate.ObserveGitDiffSince` includes `ObserveGitDiff` (every currently-uncommitted path, unconditional on `baseSHA`) merged with the committed diff since `baseSHA`. Since a real developer's workspace is routinely dirty when a Flow starts, the original check would escalate "planner changed N files" on a workspace the planner never touched — making the freeze node unusable outside a pristine tree, and contradicting `baselineWorktreeFingerprint`'s own stated reason to exist ("a Flow can freeze against an uncommitted tree"). Fixed by capturing a dirty-file content fingerprint once at flow start (`interactiveRun.flowStartWorktreeFingerprint`, set in `startResolvedFlow` alongside `flowStartGitHead`) and diffing a fresh fingerprint against it via the new `worktreeMutatedSincePaths` — a path absent from the baseline, or present with a different hash, is a real mutation; a path dirty in both with the same hash is pre-existing and not the planner's doing. `TestRunContractFreezeNodeAllowsPreExistingDirtyWorktree` (new) proves a pre-existing dirty file no longer blocks the freeze; `TestRunContractFreezeNodeRejectsPlannerChangedFiles` was corrected to write its mutation *after* the baseline is captured (it previously wrote the file before the run was even created, which the reviewer correctly pointed out proved the bug's false-positive behavior rather than real detection).
- **CORRECTION (Critical, C-2): a spawn failure in `advanceFlowThroughFreezeChain` returned `false` unescalated**, directly contradicting `runContractFreezeNode`'s own documented invariant ("the legacy note+reinvoke-hub fallback must never see an unbound writer dispatch for this behavior") — a `false` here propagates through `tryAdvanceFlowThroughInline`/`tryAdvanceFlowFromNode`/`advanceOrNotifyHub` straight into the AI-driven hub-reinvoke fallback, which could then dispatch a writer through a path with no knowledge of the just-frozen contract, with the freeze step already marked Done and no escalation raised. Fixed: the spawn-failure path (and every failure path in this function) now calls the same `escalate(...)` pattern `runContractFreezeNode` uses and returns `true`.
- **CORRECTION (Critical, C-3): any registered inline-scope node in the middle of the chain was silently marked Done without ever executing**, not just `context.produce` — `resolveFreezeWriterTarget` admitted any `BehaviorScopeInline` id as a valid intermediate hop, but `advanceFlowThroughFreezeChain` only ever had real dispatch logic for `context.produce`; a hand-authored (or future) topology routing `command.validate` or `artifact.audit_draft` through this chain would have that safety node rubber-stamped Done — tests silently skipped, an audit silently marked passed — with no actual execution. Fixed: `resolveFreezeWriterTarget`'s admission switch now accepts only `context.produce` as an intermediate hop and only `agent.code` as the terminal writer (folding in M-5 below); anything else fails closed. `TestInlineChainRejectsNonContextProduceIntermediateHop` and `TestInlineChainRejectsNonAgentCodeTerminal` (both new) pin this directly.
- **CORRECTION (Critical, C-4): the two duplicate-delivery/recovery tests asserted against a stale, pre-call `FrozenStore` instance**, which cannot see what a *later* call to `runContractFreezeNode` wrote (each call opens its own store instance; `FrozenStore` loads its in-memory maps once at construction and never re-reads disk). Both tests would have passed identically whether the reuse-check logic existed or not — verified directly by temporarily disabling the reuse-check block and re-running: both tests failed as expected ("got 2" instead of "got 1" version), then passed again once the block was restored, proving the fix is load-bearing rather than another unverified claim. Fixed: both tests now open a fresh `NewFrozenStore` immediately before their assertions.
- **Addition (Important, I-1): concurrent deliveries of the same freeze-node completion could race across two separately-opened `FrozenStore` instances**, each with its own in-memory "does this exist" view — `FrozenStore`'s own path-keyed mutex only serializes the physical NDJSON append, not this runner-level check-then-decide sequence. Fixed with a new in-process mutex (`runContractFreezeNodeLockFor`, keyed by `parentRunID + freezeNodeID`) held across the open-check-freeze-save sequence in `runContractFreezeNode`. This closes the same-process race; a second OS process is still out of scope, matching Task-264's own documented multi-process-locking deferral.
- **Addition (Important, I-2): no `loopIsAdvancing` guard before the freeze proceeds** — the BUG-234 class of bug (documented at `tryAdvanceFlowFromNode`'s own top) where a completion that arrives while the loop has settled (blocked/paused/stopped) can still advance a settled loop. Fixed: `runContractFreezeNode` now checks `loopIsAdvancing` alongside the existing terminal-run check, and `advanceFlowThroughFreezeChain` re-checks both immediately before the writer spawn (I-11 folded in here — the context-production hop can take real time).
- **Addition (Important, I-4): the freeze version was hardcoded to `1`**, which would permanently collide with an old (superseded/abandoned) version's `ContractID` once P-4/P-5 land those transitions (`ComputeContractID` does not include `DeclaredAt`), locking the step out of ever freezing again after its first version is retired. Fixed: version is now derived as `len(store.ListVersionsForStep(...)) + 1`.
- **Addition (Important, I-6): a freshly-built `context.produce` package was silently discarded whenever `rs.planContextPackage` was already non-nil** (e.g. an earlier plan-stage package), even though the contract-scoped package built here — seeded with the frozen `DeclaredPaths` — is supposed to be authoritative for the coder that follows. Fixed: the nil-guard was removed; the freeze-chain's own package now always overwrites and always emits its `EventFlowContextPackage`.
- **Addition (Minor, I-10 / prompt fencing): `contract-planner.md` told the model not to use a markdown fence while showing its own JSON schema inside one**, which an LLM reliably mimics over the surrounding prose. Fixed: the schema now appears as a plain unfenced line with an explicit "single line, no fence" instruction.
- **Addition (Minor, M-1 / hop-limit off-by-one): the doc comment and CA-426's own original description both said `flowInlineChainHopLimit` bounds "6 intermediate hops," when each loop iteration consumes one edge including the final edge into the writer — the true admitted-intermediate-count is `flowInlineChainHopLimit - 1` (5, at the current value). Fixed the doc comment and added exact-boundary tests (`TestInlineChainAcceptsExactlyAtHopLimitBoundary`, `TestInlineChainRejectsOneMoreThanHopLimitBoundary`) alongside the original well-past-the-limit test, which is kept as-is (still a valid, if looser, regression case).
- **Addition (Minor, M-2 / vacuous rejection assertion): `TestRunContractFreezeNodeRejectsUnknownCoderTarget` asserted `GetFrozenForStep(runID, "any")` was not found — `"any"` never existed in the fixture, so this passed regardless of what was actually frozen. Fixed to assert `frozen_contracts.ndjson` does not exist at all.
- **Accepted/deferred, not fixed in this pass:**
  - **I-3 (fail-open on a git-observation error):** the rewritten mutation check no longer has a distinct "observation error" branch to fail closed on — `baselineWorktreeFingerprint`/`uncommittedChangedPaths` soft-degrade to `nil` on any git failure (non-repo, git absent, transient error), matching CP-54 P-2's own established non-fatal doctrine for this same helper. A `nil`-vs-`nil` diff reads as "clean." Closing this fully would mean changing `uncommittedChangedPaths`'s shared, already-relied-upon nil-on-error contract — out of scope for this task; noted here rather than silently accepted as fixed.
  - **I-5 (reuse check can't distinguish redelivery from genuine re-planning on a retry loop):** correct as identified, and explicitly a CP-55 P-4 concern (P-4 adds "amendment transition that supersedes the prior version" — the mechanism that should replace this task's blunt reuse-on-any-match with an explicit amend/retry signal). Not fixed here; flagged directly in Task-265's Open Questions for P-4 to pick up.
  - **I-7 (`baselineWorktreeFingerprint`'s inherited 20-path cap and unbounded file read):** both inherited from the pre-existing, separately-reviewed `uncommittedChangedPaths` (Task-246/CP-54 P-2) rather than introduced here; changing that shared helper's cap or adding a read-size limit is out of this task's scope.
  - **I-8/I-9/M-3/M-4/M-6/M-7:** I-8 was the same root cause as C-1 and is resolved by the C-1 fix; I-9 (escalate() logging rather than surfacing an `applyFlowControl` failure) matches the pre-existing convention every sibling function in this file already uses (`runValidateNode`/`runAuditNode`), not a new gap; M-3/M-4 are test-framing notes on tests that still pass and were left as the reviewer suggested ("acceptable but worth noting"); M-6 raised no actionable issue; M-7 (provider-side tool-allowlist enforcement for the planner) is noted as worth confirming before CP-55 P-8, not this task's own scope.
