# CA-430 — Wire Ranking Into Feature.History (Task-269, CP-55 P-7)

## Scope

Implemented [Task-269](../requirements/08-Task/done/Task-269-Wire-Ranking-Into-Feature-History.md) (P-7 of [CP-55](../requirements/07-Coding-Plan/done/CP-55-Flow-First-Preflight-Contract-Context-Retrieval-And-Canonical-Acceptance.md)): adds `HistoryRankingConfig`/`SelectHistoryEntries` (the selection layer on top of CP-55 P-6's `ScoreHistoryEntry`/`RankHistoryEntries` primitives) and `HistorySlotRanked` (the renderer), then wires both into the live `feature.history` context source — `featureHistorySource.Fetch` now builds a `RetrievalLocus` from the run's declared Contract, uncommitted diff, and prompt (via the previously-unwired `buildRetrievalLocus`, CP-54/CP-55 P-2), and renders history ranked by code-locus overlap once a feature has more candidate entries than the activation threshold, falling back to the pre-existing recency-only output otherwise.

A dedicated Claude-agent review found **0 Critical, 8 Important, and 9 Minor findings** — a **CONDITIONAL PASS**. The core mechanism (activation boundary, empty-locus short-circuit, the `Collect`-level disabling guarantee, the contract-store-independent locus building) was verified correct by direct reading, but the review found real defects in the rendering/selection edges the invariants exist to protect — most notably, the "current truth" entry could silently lose its excerpt and its enforcement instruction in ranked mode, and a zero-value `Limit` silently disabled the output cap entirely. All 8 Important findings are fixed in this same note, each verified via mutation testing (temporarily reverted, the corresponding test confirmed to fail, then restored to pass); all 9 Minor findings are addressed inline or explicitly accepted/deferred.

## Design notes

- **The routing/disabling contract is entirely at the `ContextSourceRegistry.Collect` layer, not inside `Fetch` itself.** `Collect` only calls `Fetch` for IDs present in its `enabledIDs` argument (`context_source_registry.go:104-123`) — a source absent from that list never has `Fetch` invoked at all. This means `featureHistorySource.Fetch` needs no internal "am I disabled" check to satisfy the spec's "do not run history ranking for output" requirement when `feature.history` is disabled: the ranking work simply never executes. Verified directly by the reviewer reading `Collect`'s implementation, and pinned by `TestFeatureHistoryProducesNoOutputWhenSourceIsDisabled`'s post-review call-counting strengthening (Finding I-8).
- **"The contract store can feed locus even when its rendered source is disabled" holds by construction, with no fix needed.** `buildRetrievalLocus` calls `changecontract.OpenStoreReadOnly(workspace)` directly — a fresh `*Store` with no shared cache, no dependency on `changeContractSource`'s own registration or enablement. Verified directly by the reviewer (no package-level cache, no singleton, no ordering coupling) and by `TestFeatureHistoryRanksWhenChangeContractRenderingIsDisabled`, which registers only `feature.history` in a fresh registry and confirms ranking still activates from the Contract store alone.
- **CORRECTION (Claude-agent review pass 1, Important — Finding I-1): a real double-fetch on the fallback path (the overwhelmingly common case).** The original `HistorySlotRanked` read the ledger once to decide fallback-vs-ranked, then called `HistorySlot` — which read the ledger a SECOND time to render. Every fallback call (i.e. every feature below the activation threshold) paid the full cost of `GetFeatureHistory` (a complete map copy + sort under a mutex) twice. The byte-identity guarantee also technically depended on the two reads agreeing, which the `historyLedger` interface never required. Fixed: the fallback path now renders directly from the entries slice already in hand (`renderHistorySlotChronological`), making the byte-identity guarantee hold by construction from a single read, and halving the ledger-read cost for the common case.
- **CORRECTION (Claude-agent review pass 1, Important — Finding I-2): the ranked-mode header silently dropped the enforcement instruction the legacy header carried.** The legacy header ends "`build on the NEWEST, do not undo it`" — not decoration, but the prompt-level enforcement of SD-17 D-3 ("newest = current truth"). The original ranked header replaced this with only a candidate-count note, leaving the model with a non-chronological list and no instruction about which entry to trust or that the list is even unordered by time. Fixed: the ranked header now explicitly states the list is not chronological and names the current-truth marker as the one to build on.
- **CORRECTION (Claude-agent review pass 1, Important — Finding I-3): the "current truth" entry could lose its excerpt exactly when the invariant it protects matters most.** The excerpt budget in ranked mode was gated on rank position (`i < recentHistoryExcerptCount`) — but the newest entry is deliberately force-included precisely when its locus score is LOW, meaning it is the entry MOST likely to rank outside that budget. Its `CAExcerpt` (the "why" a reviewer or coder most needs in order not to undo the current state) was silently dropped in exactly that case. Fixed: the current-truth entry's excerpt is now unconditional, independent of rank. **Mutation testing note**: the first fixture written for this fix accidentally always passed regardless of the fix, because the companion positioning fix (backfilled newest → front of list) already put the backfilled entry inside the top-3 excerpt window by coincidence. The test had to be redesigned with a fixture where the newest entry is NATURALLY selected (not backfilled) at rank position 4 — four other, older entries each scoring a higher locus overlap rank ahead of it — to actually exercise the position-independent excerpt guarantee. This is recorded because it is itself a small instance of the review's own recurring theme: a plausible-looking fixture can pass for the wrong reason, and only actually reverting the fix and watching the test still pass proves the gap.
- **CORRECTION (Claude-agent review pass 1, Important — Finding I-4): a `Limit` of 0 (Go's own zero value) was read as "no cap," not "use the default."** `if limit <= 0 || limit > len(ranked) { limit = len(ranked) }` conflated "not set" with "exceeds candidate count," resolving both to zero bound. Any caller constructing a `HistoryRankingConfig` with only `ActivationThreshold` set — a very easy mistake — got every ranked candidate rendered uncapped, silently defeating the one guarantee the legacy renderer enforced unconditionally ("a feature with hundreds of commits injects a bounded block, not the full chronology"). Fixed: a non-positive `Limit` now falls back to the package's own default `Limit` before the len-clamp is applied.
- **CORRECTION (Claude-agent review pass 1, Important — Finding I-5): `DefaultHistoryRankingConfig` was an exported, mutable package-level `var`.** Any package in the binary — including an unrelated test running in the same process — could reassign it and silently change ranking behavior process-wide, a `architecture-skill` "no global mutable state" violation. Fixed: the value now lives in an unexported var and is exposed only via a function returning a fresh copy, so no caller can hold a reference to shared mutable state. This is a deviation from the coding-plan doc's own illustrative `var DefaultHistoryRankingConfig = ...` snippet — a deliberate one, made for the reason above, since the doc's snippet was illustrative of the intended values, not a binding API-shape requirement, and no test signature in the spec was anchored to it being a var specifically.
- **Addition (Claude-agent review pass 1, Important — Finding I-6/I-7/I-8): three tests strengthened to actually discriminate correct from plausible-but-wrong implementations.** `TestSelectHistoryEntriesKeepsNewestAbsoluteTruth` previously asserted only presence, which a broken backfill (duplicating the entry, or appending it past the cap) would also satisfy — now asserts exact length, exactly-once presence, and position. `TestFeatureHistoryProducesNoOutputWhenSourceIsDisabled` previously proved only "no section returned," which a wasteful implementation that computed the ranking and discarded it would also satisfy — now proves zero `Fetch` invocations via a counting decorator, with a positive control. (Finding "I-6," the reviewer's own count of new tests not matching the review-dispatch prompt's approximate wording, was a review-prompt imprecision rather than a real documentation drift — no phase document existed yet at review time to have drifted from; this document reports the accurate, final count.)
- **Accepted/deferred, not fixed in this pass (Claude-agent review pass 1):**
  - **Finding M-1 (a non-discriminating test fixture in `TestFeatureHistorySourceBuildsLocusFromFrozenContract`)**: fixed, not deferred — see the fix-pass bullet above.
  - **Finding M-2 (newest-entry identity tracked by `CommitHash` string equality, not immune to a theoretical multi-empty-hash collision)**: the `candidateCount == 0` guard closes the reachable panic path; the residual hash-collision risk is accepted as genuinely unreachable from every real caller (`changeledger.Ledger` is keyed by commit hash, so duplicates — including duplicate empty hashes — cannot occur via its own `Upsert`/`GetFeatureHistory` path) and would require a larger index-tracking refactor of `RankHistoryEntries`'s public return shape to close for an arbitrary caller-supplied slice, disproportionate to a Minor, currently-unreachable finding.
  - **Finding M-4 (residual `CommittedAt` string-vs-instant ordering divergence between this task's `CommitUnix`-based ranking and `changeledger.GetFeatureHistory`'s own string-based ordering)**: already disclosed in P-6's own doc comment (CA-429); the residual gap (a non-UTC-offset `CommittedAt` written by some future caller) is real but requires either normalizing `Ledger.Upsert`'s input or accepting the documented divergence — recorded as an open question, not resolved by this task, since fixing it belongs to `changeledger` ownership, not this task's own scope.
  - **Finding M-9 (two divergent history renderers now coexist — the Flow context-package path is ranked, the non-Flow per-turn injection path via `composeFeatureBlocks`/`HistorySlot` remains recency-only)**: correct as identified, and consistent with this task's own stated scope ("wire ranking into the `feature.history` context source"). Recorded explicitly here as a known, deliberate asymmetry — candidate scope for a later phase, not silently left unmentioned.
