## AI Quick View

### Summary

- Found during live CP-36 Scenario 9 verification on `run-13821`: after reviewer feedback triggered `continue`, the re-entered coder's generated content appeared in both the coder sub-agent transcript and the main hub transcript.
- The core reason was stale loop state. `applyFlowControl("continue")` only reset the loop to `running` from `""` or `blocked`; if the previous verdict status was `rejected`, the new round still carried `Status="rejected"`.
- The same hub provider turn also submitted another `flow_control` (`escalate`) after `continue`, which blocked the loop while the coder was already running.
- When the coder finished, `tryAdvanceFlowFromNode` saw the loop as non-advancing and refused to spawn the next reviewer cohort, falling back to hub notification with the coder result as prompt context. The main hub then surfaced essentially the same content as the coder.

### Current Ask

- Prevent coder reentry output from being duplicated into the main chat.
- Preserve the intended Scenario 9 behavior: after `continue`, coder completes, then downstream reviewers run again instead of the hub consuming coder output directly.

### Key Decisions

- `V-1` `continue` always starts a fresh active loop round and clears stale verdict/block metadata unless the cap is hit.
- `V-2` one provider turn may submit only one flow-control decision; later decisions from the same turn are rejected so a stale `escalate` cannot overwrite a just-started coder round.
- `V-3` Keep the fix backend-first. No frontend filtering is needed for this case because the duplicate content was caused by backend orchestration falling into the wrong fallback path.

### Constraints

- Do not disable legitimate hub synthesis after reviewer cohort join.
- Do not break cap handling: `continue` at cap still blocks and awaits the user.
- Do not remove parent timeline spawn cards for re-entered children; BUG-242 requires those cards.

## 6. Root Cause

- confirmed cause 1: `applyFlowControl("continue")` reset loop status to `running` only when prior status was empty or `blocked`. Prior reviewer verdicts can set the loop to `rejected`, so a new round could start while still marked non-advancing.
- confirmed cause 2: `SubmitFlowControl` did not reject multiple flow-control calls from the same provider turn. In `run-13821`, the hub submitted `continue` and later `escalate`; the latter stale decision blocked the loop while coder reentry was already running.
- confirmed evidence from `run-13821`:
  - `04:47:12`: `flow_control_continue` returns `next_action="looping"` but logs `loop_status="rejected"`
  - `04:48:34`: same flow receives `flow_control_escalate` and becomes `blocked`
  - `04:49:06`: coder completion logs `flow_advance_skipped_loop_blocked` for `completed_node_id="coder-gpt"`

## 7. Fix Strategy

- `F-1` In the non-cap `continue` branch, always set loop `Status="running"` and clear stale `BlockReason`/`GateReason`.
- `F-2` In `turnBridge.SubmitFlowControl`, reject a second flow-control submission from the same provider turn before it can mutate the parent loop.
- `F-3` Add regression tests for both the stale `rejected -> continue` transition and duplicate flow-control submission.
