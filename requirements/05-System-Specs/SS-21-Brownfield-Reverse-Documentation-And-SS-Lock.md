## AI Quick View

### Summary

- Establish the business rules and safety boundaries for **onboarding brownfield/legacy codebases** into FlowPilot via the unified `/standardize [scope]` command.
- Solves the cold-start problem: turning un-documented or loosely-documented repositories into structured `SS/SD/CP/Task` specifications.
- **The Hard Ceiling Rule**:
  - Source code only reflects *WHAT* the system currently does; it cannot reveal *WHY* the business intended it that way.
  - The AI is allowed to reverse-engineer technical designs (**SD**) and implementation tasks (**CP/Task**) from source code and GitNexus call-graphs.
  - The AI **MUST NEVER FABRICATE** business requirements or System Specs (**SS**). It only drafts skeleton SS templates marked with `TODO: human intent needed`.
- **The Non-Bypassable SS-Lock Gate**:
  - Execution must pause at `SS-Lock Gate` (`ss_lock_gate.go`).
  - The human operator must review, amend, and explicitly confirm/lock the System Specs before any coding or sprint automation proceeds.

### Key Decisions

- `AC-1` **Anti-Hallucination Ground Truth**: Technical designs generated by reverse-documentation must cite explicit symbols, files, and Git commit hashes as evidence.
- `AC-2` **Human Sovereignty on Business Intent**: Business intent (SS) cannot be auto-generated without human lock (`user.confirm`).
- `AC-3` **3-Tier Standardization Repair**:
  - Auto-Fix: Deterministic Go codemod for formatting and skeleton headers.
  - Assisted-Fix: LLM semantic completion with mandatory diff review.
  - Manual-Flag: Flagging severe architectural conflicts for operator resolution.

---

## 1. Goal

Enable teams with existing codebases (brownfield projects) to quickly establish full FlowPilot compliance, retroactively generating high-fidelity technical specs while strictly protecting business intent from AI hallucination.

## 2. Problem

When adopting AI in existing projects, developers either:
1. Have no specs, so AI writes code based on shallow guesses.
2. Let AI hallucinate full business specs from code, embedding legacy bugs and tech debt as "intended requirements".

## 3. Scope

- In scope:
  - The `/standardize` CLI/TUI command.
  - Reverse extraction of SD and Task specs from code and GitNexus graph.
  - Mandatory SS-Lock Gate.
- Out of scope:
  - Decompiling binary code or third-party proprietary libraries.

## 4. Acceptance Criteria

- `AC-1` Running `/standardize [scope]` on un-documented code must generate draft SD and CP specifications containing explicit source citations.
- `AC-2` Any draft SS generated must mark all business rules and acceptance criteria with explicit human confirmation placeholders.
- `AC-3` The runner must block subsequent execution until the user completes the `SS-Lock` confirmation via the Desktop App or Terminal TUI.
