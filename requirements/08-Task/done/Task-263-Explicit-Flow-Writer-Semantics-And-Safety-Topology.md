## AI Quick View

### Summary

- Adds the two canonical behavior ids CP-55 needs for a Flow preflight-contract lifecycle: `agent.code` (explicit project-mutation marker) and `contract.freeze` (Go-owned validation+persistence marker, fail-closed placeholder in this slice).
- Adds a static Flow safety-topology validator (`ValidateFlowSafetyTopology`, `ForwardDominates`, `EveryDonePathIncludesAcceptance`) wired into the existing `ValidateFlowDefinition` check, so it runs at every current definition-resolution boundary for free.
- No built-in flow YAML is migrated. A flow with zero `agent.code` nodes always passes the new validator unchanged — this is the P-1 compatibility strategy the rest of CP-55 depends on.

### Key Decisions

- `T-1` **Self-mapping aliases only, no existing alias touched.** `agent.code`/`contract.freeze` are added to `agentpack.behaviorAliases` as `"agent.code": "agent.code"` and `"contract.freeze": "contract.freeze"`. GitNexus impact flagged `NormalizeBehaviorID` CRITICAL (11 direct callers, 56 impacted symbols, 5 processes, 3 modules) before this edit; every pre-existing alias->canonical mapping is pinned by a new regression test (`TestNormalizeBehaviorIDExistingAliasesUnchanged`, `TestExistingBehaviorAliasesStillResolveUnchanged`) so the CRITICAL fan-in cannot silently regress.
- `T-2` **`agent.code` reuses `behaviorAgentDelegate` verbatim.** Same handler function, same registered scope (`BehaviorScopeDelegate`) — CP-55 3.5 requires the provider payload stay byte-identical to `agent.delegate`; only topology/gate treatment differs, and that lives outside the handler. Proven by `TestAgentCodeReusesDelegateDispatchWithoutChangingProviderPayload`.
- `T-3` **`contract.freeze` is a fail-closed placeholder, not a no-op.** Registered with `BehaviorScopeInline` and a handler that unconditionally returns an error. The real validation+persistence handler (parse planner draft, validate, bind run/step/baseline, persist durably) is CP-55 P-3. No built-in flow node references `contract.freeze` yet, so this path is not reachable at runtime until a later slice wires a real node to it — the placeholder exists only so `NewDefaultBehaviorRegistry` can resolve the id today.
- `T-4` **Topology validator lives in `agentpack`, not `runner`.** `ValidateFlowSafetyTopology`/`ForwardDominates`/`EveryDonePathIncludesAcceptance` operate on `FlowDefinition` (already in `agentpack`) using plain-string canonical ids resolved through the existing `NormalizeBehaviorID`. `agentpack` cannot import `runner` (`runner` already imports `agentpack`), so the runner-side typed `BehaviorID` consts (`BehaviorAgentCode`, `BehaviorContractFreeze`) are a separate, independently-verified pair of string literals — not a shared symbol — matching the same "runner → agentpack" dependency direction CP-55 §3.4 requires for `changecontract`/`featurecatalog`.
- `T-5` **Wired inside `ValidateFlowDefinition`, not at the resolver call sites.** `ValidateFlowDefinition` already runs at every current definition-resolution boundary (`LoadFlowFS`, and both `FlowDefinitionResolver.ResolveFlowRef`/`ResolveBuiltin`, which call it directly). Adding one call inside it, rather than editing the three call sites separately, satisfies CP-55's "wire validation at the same definition-resolution boundaries" with a single, minimal, low-risk edit (`ValidateFlowDefinition` impact: LOW, 3 impacted, 2 processes) instead of three.
- `T-6` **Compatibility is structural, not a special-cased flag.** `ValidateFlowSafetyTopology` classifies writer/freeze nodes first; if a flow has zero `agent.code` nodes it returns `nil` immediately. Since P-1 does not migrate any built-in flow YAML, every existing flow (built-in or user-defined) has zero `agent.code` nodes today, so every one of them passes unchanged — proven directly against the real embedded pack (`TestValidateFlowSafetyTopologyAcceptsAllBuiltinFlowsUnchanged`) rather than assumed.
- `T-7` **Acceptance is a Flow-declared boundary (`AcceptanceNodes`), verified by full forward-path traversal — not a direct-edge check.** Codex review pass 1 (see [CA-424](../../../change-audit/CA-424-explicit-flow-writer-semantics-and-safety-topology.md)) found the original claim false: checking only the writer's own direct edges lets a non-acceptance intermediate node (`writer -> validate -> done`) pass, since `validate` is not literally `"done"`. The fix adds an optional `AcceptanceNodes []string` field to `FlowDefinition` (root YAML key `acceptance_nodes`); a flow declaring any `agent.code` writer must set at least one entry naming a real, non-writer node. `EveryDonePathIncludesAcceptance`/`everyForwardPathFromWriterCrossesAcceptance` then walks every forward path from the writer's own outgoing edges with state `(node, hasCrossedAcceptance)`, rejecting any path that reaches terminal `"done"` before crossing a declared acceptance node. Acceptance crossed only upstream of the writer does not count, and a mixed branch fails if any one branch bypasses acceptance. Legacy flows stay compatible because none declare an `agent.code` node, so the new requirement never triggers for them.
- `T-8` **`forwardDominatesFrom` fails closed instead of vacuously dominating.** Codex review pass 1 found a CRITICAL gap: the original BFS returned `true` whenever it simply never visited the target, which is also what happens when the target is unreachable from any entry at all (absent ids, a flow with zero entries, or a writer/freeze pair stranded in a forward cycle disconnected from every real entry). The fix requires both ids to be declared nodes and requires the target to be proven reachable from a real entry (`reachableFromAnyEntry`) before any dominance verdict is returned — a writer-containing graph with no entry, or a writer/freeze cycle disconnected from every real entry, now fails validation instead of silently passing. Pinned by `TestForwardDominatesRejectsAbsentDominatorID`, `...RejectsAbsentTargetID`, `...RejectsUnreachableWriter`, `...RejectsNoEntryForwardCycle`, `...HandlesMultipleEntriesAllFunnelingThroughDominator`, `...HandlesMultipleEntriesOneBypassingDominator`, `TestValidateFlowSafetyTopologyRejectsNoEntryForwardCycleContainingWriter`, and `...RejectsWriterFreezeCycleDisconnectedFromRealEntries`.
- `T-9` **No executor wiring in this slice.** Read `flow_executor.go`'s `startInlineEntryChain`/`tryAdvanceFlowThroughInline` before editing anything: both already gate on `BehaviorScope` (`agent.code`'s `BehaviorScopeDelegate` correctly fails the inline-entry `BehaviorScopeInline` check, so a writer can never be misclassified as an auto-startable inline entry). One fallback branch in `tryAdvanceFlowThroughInline` (around `flow_executor.go:1069`) hardcodes `canonical != "agent.delegate"` to reject non-delegate spawn targets — this will need to accept `"agent.code"` too once a real flow uses it (P-3/P-4), but is out of scope now since no node selects `agent.code` yet.
- `T-10` **`AcceptanceNodes` round-trips through the desktop Settings direct-to-Supabase path too, not just the Go-backed store (Codex review pass 3).** Pass 2 added `workflows.acceptance_nodes_json` and wired `dbWorkflowRow`/`recordFromWorkflowRow`/`SupabaseWorkflowFlowStore.Upsert` in `apps/local-runner`, but the desktop Settings UI (`apps/desktop-flowpilot`) never goes through that Go store at all — it talks to Supabase directly via `packages/flowpilot-client-core`'s `SupabaseAdminRepository`, which had no `acceptanceNodes` field on `Workflow`, and whose `mapWorkflow`/`saveWorkflow`/`cloneWorkflow` all omitted `acceptance_nodes_json`. A plain INSERT (a fresh `cloneWorkflow` copy) with that column omitted falls back to the migration's `default '[]'::jsonb` regardless of what the source actually declared — the "loses the mandatory safety boundary" gap Codex pass 3 found. The fix: `Workflow.acceptanceNodes?: string[]` (optional, additive) in `adminModels.ts`; `mapWorkflow` reads `acceptance_nodes_json`; `saveWorkflow`'s upsert payload and `cloneWorkflow`'s insert payload both send `acceptance_nodes_json` (`?? ## 1. Goal

Give the Flow engine a real, non-heuristic way to say "this node mutates the project" (`agent.code`) and "this node is the Go-owned gate that must run before it" (`contract.freeze`), plus a static validator that can reject an unsafe topology before execution — without touching, migrating, or behaviorally changing any flow that exists today.

## 3. Trigger

CP-43's temporal-contract-gap problem (a contract declared after code already changed is not a pre-commitment) cannot be closed until the runtime can tell, from the flow graph alone, which node is the writer and which node must freeze the contract before it runs. That distinction does not exist yet — code-writing detection is currently a prompt/node-name heuristic. This task adds the explicit graph-level markers and the static safety pass that later CP-55 slices (P-2 through P-8) build on.
