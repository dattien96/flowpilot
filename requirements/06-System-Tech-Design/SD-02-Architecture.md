# FlowPilot - System Architecture

This document defines the high-level system architecture of FlowPilot, based on the technology stack defined in `SD-01-Tech-Stack.md`. 

The system utilizes a decentralized Execution Model (Runner) combined with a centralized State and UI layer to safely and efficiently execute AI workflows.

## 1. High-Level Architecture Overview

FlowPilot operates on a **3-Tier Architecture** with a memory layer inside the backend/control plane:
1. **Client / Frontend:** A React SPA that provides the dashboard for configuring workflows, viewing artifacts, and managing approvals.
2. **Backend / Control Plane:** Supabase acts as the central source of truth for user data, workflow definitions, states, and file storage.
3. **Execution Runner (Golang):** A lightweight CLI worker running on the user's local machine or within a Docker container. It pulls tasks from the backend, talks to the AI LLMs, executes code/skills locally, and pushes the results back.

---

## 2. Frontend Architecture (React + Vite)
The frontend serves as the main user interface for Developers, Leaders, and PMs to orchestrate the AI.

- **Framework:** React 19 + Vite with TypeScript for fast, type-safe SPA development.
- **Routing:** TanStack Router (file-based, type-safe) for handling navigation between projects, workflows, and artifact viewers. Auth guards use `beforeLoad` hooks.
- **State Management:** 
  - **TanStack Query:** Handles all asynchronous state fetching from Supabase, caching, and real-time UI invalidation.
  - **Zustand:** Manages lightweight, synchronous UI state (dark mode, sidebars, active selections).
- **UI & Styling:** Tailwind CSS 4 coupled with shadcn/ui provides highly reusable, accessible components for building complex workflow builders and dashboards.
- **Forms & Validation:** Zod schema validation ensures robust data entry for configuring steps and agent parameters.

---

## 3. Backend & Control Plane (Supabase)
Supabase eliminates the need for a traditional monolithic API, serving as a robust Backend-as-a-Service (BaaS).

- **PostgreSQL Database:** Stores user profiles, projects, workflow definitions, step configurations, and workflow execution states (e.g., `RUNNING`, `WAITING_USER_APPROVAL`, `DONE`).
- **Auth:** Handles secure login and row-level security (RLS) to ensure users can only see their own projects and workflows.
- **Storage:** Stores the actual Markdown and JSON Artifact files generated by the workflows securely in the cloud.
- **Artifact Memory:** Stores structured working memory extracted from raw artifacts, including summaries, key decisions, constraints, source references, and vector embeddings for retrieval.
- **Realtime:** Subscribes the Frontend to database changes, so the UI updates instantly when the Golang Runner completes a step or updates a workflow's status.
- **Edge Functions:** Used for lightweight server-side operations, such as triggering webhooks, initiating secure state transitions, and generating embeddings for artifact memory.

---

## 4. Execution Runner Architecture (Golang)
The actual AI execution, prompt construction, and skill execution do NOT happen in the browser or on Supabase. They happen via a Golang CLI tool to ensure local environment access.

- **Golang + Cobra:** A robust, performant CLI tool deployed locally (or in Docker). It polls or receives events from Supabase to pick up pending workflow steps.
- **Why Local/Docker?** The runner needs access to the user's local file system to read the codebase context, save local custom skills (to `.claude/`, `.codex/`, `.gemini/`), run tests (e.g., during the TDD step), and compile code during the Code/Review Loop.
- **Responsibilities:**
  1. Pull the step instructions, skills, and context (Jira, Figma, local code).
  2. Resolve prompt memory by selecting working memory, MCP context, user context, and required artifact excerpts.
  3. Construct the final prompt and call the configured AI Provider (Gemini, Claude, or Codex).
  4. Parse the output and execute any local terminal commands (like compiling the project).
  5. Push the generated Artifact, working memory, prompt-context audit records, and status back to Supabase.

---

## 5. End-to-End Execution Flow (Example)
Here is how the three components interact when a user triggers a workflow:

1. **Trigger:** User clicks "Start Bug Fix Flow" on the **React Frontend**.
2. **State Update:** Frontend inserts a new workflow run record into **Supabase Postgres**. State is set to `PENDING`.
3. **Dispatch:** The **Golang Runner**, authenticated with Supabase on the host machine, detects the `PENDING` job. It updates the state to `RUNNING` via Supabase (which instantly updates the Frontend UI via Realtime).
4. **Execution:** The Runner pulls the Jira context, builds the prompt, and queries the **Gemini API**. It writes the fixed code to the local file system and runs the unit tests.
5. **Artifact Upload:** The Runner generates a Root Cause Analysis `.md` file and uploads it to **Supabase Storage**.
6. **Approval Gate:** The Runner updates the workflow state to `WAITING_USER_APPROVAL`. The Frontend displays the Artifact and an "Approve" button.
7. **Continuation:** Once the Leader clicks "Approve", the state shifts back to `PENDING`, and the Runner picks up the next step.
